# LibraTrack — чат персоналу бібліотеки

Lesson 14 WebSocket: онлайн-чат інтегровано в наявний вебзастосунок
обліку бібліотеки. Каталог, REST API, PostgreSQL, ролі та браузерний вхід
працюють разом із чатом в одному Go-сервері.

Початкова версія в `main` — завершений Lesson 10, коміт
`b75b1c0a89936a14851c896d1afe856d653bb754`, без звітів і матеріалів розробки.
WebSocket-розширення розробляється в `develop` і подається через PR у `main`.
Вкладення Examples у LMS містило приклади іншої теми, тому практику
реалізовано за матеріалами Lesson 14 на основі власного застосунку.

## Локальний запуск

Потрібні Go **1.27.3** (або автоматичне завантаження Go toolchain),
Docker Desktop із Compose v2 та Python 3. Команди виконуються в корені проєкту:

```bash
python3 scripts/setup_env.py
docker compose up -d --wait --build postgres
go run ./cmd/demo-users
go run ./cmd/api
```

- Каталог: <http://localhost:8088/catalog>
- Вхід: <http://localhost:8088/login>
- Чат: <http://localhost:8088/chat>
- Swagger: <http://localhost:8088/swagger/index.html>
- REST API: <http://localhost:8088/api/v1/books>

Setup генерує випадкові секрети в ігнорованому `.env` із правами `0600`.
Демоакаунти `reader14`, `librarian14`, `admin14` і `colleague14` мають email
`ім’я@example.com`. Акаунт colleague має роль librarian. Випадкові паролі
зберігаються у `../lesson14-artifacts/.demo-accounts.txt` поза репозиторієм.
Для іншого зовнішнього каталогу задайте `ARTIFACTS_DIR` перед командою
`demo-users`. Повторний запуск зберігає вже наявні облікові дані.

PostgreSQL слухає `127.0.0.1:5444`, HTTP — `127.0.0.1:8088`.
Compose використовує власний volume `libratrack14_pgdata` та бази
`libratrack14`, `libratrack14_test`, `libratrack14_migr`.
Дані попередніх уроків не використовуються. Для паузи виконайте
`docker compose stop`; наявний volume зберігається.

## Як користуватися чатом

Увійдіть як librarian або admin й оберіть «Чат персоналу» в меню.
Підключення до кімнати «Загальна» відбувається автоматично. Доступні також
«Видача книг» та «Каталог». Перехід в іншу кімнату закриває попереднє
з’єднання й відкриває нове. Повідомлення бачать лише підключені клієнти
обраної кімнати. Лічильник показує кількість з’єднань, включно з вкладками
одного користувача.

Відправник отримує серверне повідомлення разом з іншими учасниками;
інтерфейс відображає його один раз. Автор визначається з поточної
автентифікованої сесії. Клієнт не може підмінити автора чи кімнату полями JSON.
Повідомлення відображаються через `textContent`, без інтерпретації HTML.

Кнопка «Відключитися» припиняє з’єднання та автоматичні повторні спроби.
Після мережевого збою клієнт пробує перепідключитися до п’яти разів із
паузами 1, 2, 4, 8 і 10 секунд. Історія не зберігається: після перепідключення
надходять лише нові повідомлення. У вкладці зберігається до 200 повідомлень;
перехід між кімнатами очищує видимий список.

Для двох різних сесій в одному браузері можна увійти окремо через
`localhost:8088` і `127.0.0.1:8088` або використати різні профілі браузера.

## Маршрути та формат повідомлень

| Маршрут | Призначення |
| --- | --- |
| `GET /chat` | Сторінка чату для librarian/admin |
| `GET /ws/chat?room=general` | WebSocket тієї самої браузерної сесії |
| `GET /chat/stats` | Активні з’єднання, кімнати, обробники та кількість горутин для персоналу |
| `POST /logout` | Очищення cookies і закриття активних сокетів поточної сесії |

Клієнт надсилає текстовий JSON:

```json
{"text":"Колеги, книгу повернуто."}
```

Сервер надсилає події `message` та `presence`. Подія повідомлення містить
`id`, `room`, `author`, `user_id`, `text`, `time` і `online`. Час — UTC у
RFC 3339, інтерфейс показує локальний час браузера. `id` зростає в межах
поточного процесу та скидається після перезапуску.

## Конкурентність і межі

Один цикл хаба володіє всіма клієнтами й розсилає події через їхні обмежені
черги. Кожне з’єднання має один цикл читання та один цикл запису; ping
надсилає той самий записувач. Заповнення черги відключає лише повільного
клієнта. Повторне видалення клієнта безпечне. Завершення сервера окремо
закриває WebSocket-транспорти та очікує виходу обох обробників.

| Обмеження | Значення |
| --- | --- |
| Черга клієнта | 32 події |
| Усього з’єднань | 256 |
| З’єднань користувача | 8 |
| Текст повідомлення | 1–2000 Unicode символів після обрізання пробілів |
| Вхідний WebSocket message | 16 KiB |
| Частота повідомлень | до 20 за секундне вікно на з’єднання |
| Очікування pong | 45 секунд |
| Період ping | 22,5 секунди |
| Тайм-аут запису | 5 секунд |

WebSocket перевіряє роль із БД перед рукостисканням і приймає лише точний
Origin поточного HTTP-сервера. Відсутній або сторонній Origin відхиляється.
JWT передається через HttpOnly cookie, без токена в URL чи `localStorage`.
Після закінчення JWT відкрите з’єднання закривається. Logout закриває
поточні сокети, але, як і в початковому застосунку, не відкликає вже
скопійований JWT для нових HTTP-запитів.

Локально використовується HTTP. Для прямого HTTPS-запуску потрібні TLS і
`COOKIE_SECURE=true`. Обробник Origin не довіряє `X-Forwarded-*`; розгортання
за reverse proxy потребує окремої конфігурації довіреного проксі.
Хаб працює в одному процесі; спільні кімнати між репліками потребують брокера.

## Перевірки

Після запуску PostgreSQL:

```bash
bash scripts/check.sh
```

Сценарій перевіряє форматування, залежності, build, vet та виконує
`go test -race -count=1` з реальним PostgreSQL. Інтеграційні тести створюють
окремі випадкові схеми в базі `_test`. Пропущений тест або FAIL означає
помилку. JSON, підсумок і покриття записуються лише до зовнішнього
`ARTIFACTS_DIR` (типово `../lesson14-artifacts`).

Окремий запуск WebSocket-перевірок:

```bash
go test -race -count=1 -v ./internal/chat
go test -race -count=1 -v ./internal/handler/web -run Chat
```

Перевірено три клієнти, ізоляцію кімнат, серверного автора, звичайне та
раптове відключення, 100 циклів підключень, повільного клієнта, ping/pong,
закінчення сесії, logout, некоректні повідомлення, Origin, ролі, ліміти та
зупинку сервера під час реєстрації клієнтів. Початкові тести каталогу,
REST API, міграцій, CSRF і RBAC залишаються в наборі.

### Ручна перевірка

1. Відкрийте три вкладки чату. Надішліть повідомлення з однієї; перевірте
   доставку в усі три без дубліката у відправника.
2. Переведіть одну вкладку в іншу кімнату; перевірте ізоляцію розсилки.
3. Кілька разів відключіться й підключіться кнопкою. У відключеному стані
   форма недоступна; після підключення надсилання знову працює.
4. Закрийте вкладку. В іншій вкладці лічильник має зменшитися.
5. Вийдіть із застосунку. Відкриті з’єднання цієї сесії мають закритися.
6. За потреби порівняйте `/chat/stats` до та після циклів. Після очищення
   активні з’єднання й обробники мають повернутися до початкового рівня.

Чистий race-прогін перевіряє виконані шляхи; він не є доказом відсутності
всіх можливих гонок або витоків. Журнали, скриншоти й звіт зберігаються
поза репозиторієм.

## English overview

LibraTrack adds an authenticated staff WebSocket chat to the existing Go/Gin,
PostgreSQL and HTMX library application. Three rooms share one owner hub;
each socket has one reader and one writer, bounded queues, heartbeat and
explicit shutdown. Browser sessions supply the identity. Chat messages are
not persisted and only future messages arrive after reconnection.

Run `python3 scripts/setup_env.py`, `docker compose up -d --wait --build postgres`,
`go run ./cmd/demo-users`, then `go run ./cmd/api`. Open `/chat` as librarian
or admin. Run `bash scripts/check.sh` for build, vet and PostgreSQL race tests.
All credentials and verification artifacts remain outside version control;
evidence is written outside the repository.
